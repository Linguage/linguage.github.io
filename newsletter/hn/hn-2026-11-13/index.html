人工智能与市场

Anthropic 启动上市路演

Anthropic 在官网开设了首次公开发行专题页，以公益公司（public benefit corporation）定位说明融资安排，并发布创始人信、路演视频、财务摘要、客户案例与参与指南。页面列出的 2026 年第三季度财务要点包括：营收 170 亿美元、同比超过 12 倍；过去十二个月营收不低于 10 万美元的客户超过 11,900 家，同样同比超过 12 倍；自 2025 年第一季度以来，按营收相对算力与基础设施费用衡量的算力效率提升超过 4 倍。经调整营业利润率为 15%，营业利润率为负 3%；净亏损 233 亿美元，其中包含约 219 亿美元与可转债、衍生负债和 SAFE 公允价值变动有关的非现金费用。客户案例覆盖 Legora、礼来、乐天、Salesforce 与沃尔玛等。讨论区有人整理时间表：路演自 11 月 10 日（美东）开始，最终发行价预计于 11 月 18 日确定，股票预计 11 月 19 日开始公开交易。部分地区页面会按地理位置跳转到欧洲或英国通道，并非所有国家的零售投资者都能直接参与。

HN 讨论对新股估值和亏损数字反应强烈。有人强调 233 亿美元净亏中大部分是账面估值变动，实际经营亏损相对营收并不那么夸张；也有人质疑「经调整利润率」的口径，并指出未来还有巨额承诺。舆论迅速把它和黄仁勋辞职、所谓人工智能泡沫放在一起：有人担心市场难以同时消化 SpaceX、Anthropic 以及可能延后的 OpenAI 大规模上市，也有人认为英伟达股东若调仓，反而可能给这次发行带来买盘。公益公司身份被不少人视为法律标签、公众并无强制执行权。另一些评论转向产品层：大模型切换成本对个人开发者很低，对企业则因工具链绑定而更高，因此 Anthropic 可能更接近云厂商而非可随意替换的「原油」。也有用户称 Claude 已经改变了自己的工作方式，认为首页评论过于一边倒。

谷歌发布 Gemini 4 Hydrogen 与 Orchestrator

谷歌 DeepMind 于 11 月 12 日发布 Gemini 4 Hydrogen。官方把它定位为面向日常编程与智能体工作流的快速执行模型，以补足同系列前沿模型 Carbon、Argon 在长程推理上的定位，并推向 Google AI Studio、Gemini API、Gemini 商务版、Gemini 应用、搜索，以及 Antigravity 中的付费 Pro 与 Ultra 用户。在 Artificial Analysis Intelligence Index 上，Hydrogen 默认的 high 思维档为 51，高于 Argon 的 50，最高档 xhigh 可达 54。定价在整个 100 万 token 上下文窗口内统一为每百万输入 1.50 美元、每百万输出 7.50 美元。官方称，相对 Gemini 3.8 Flash，默认 high 档完成任务快约 2.5 倍，Terminal-Bench 4.1 分数从 18.2% 升至 57%，虚构陈述减少超过 5 倍。同期推出的 Antigravity Orchestrator 可在同一个任务执行过程中在 Carbon 与 Hydrogen 之间动态切换：前者做规划与排障，后者写代码、改依赖和跑测试。官方给出的 Terminal-Bench 成绩是接近 Carbon 的成功率，同时平均少消耗约 24% 配额、快约 19%。Hydrogen 提供 low、medium、high（默认）和新增的 xhigh 四档思维深度。

讨论几乎一边倒地先吐槽命名：Hydrogen、Argon、Carbon 既不按字母、也不按原子量或宇宙丰度排列，和以往 Pro/Flash 或对手「月光—行星」式层级相比更难记。有人把它理解为新一代 Flash，作为常用的执行模型，适合当子智能体；也有人觉得免费搜索与应用里用上接近前沿的模型，会抬高普通用户对「人工智能有多聪明」的观感。另一些实测并不买账：有人抱怨它仍会搞错日期时间，有人认为基准成绩好看，但在智能体工作流中更容易出现执行过度、方向相反或偏离任务等问题。也有评论肯定博文直接对比时延与单次任务成本，认为在非编程任务上可能优于 Sonnet，高推理档比 Terra 更聪明但更贵。配套的 Orchestrator 帖里，有人欢迎不用手动切模型，也有人担心把调度权交给「自我感觉良好」的模型，自己用规则绑定子智能体可能更稳。

软件工程与开发者

Jane Street：软件工程面试「稍微」改一改

Jane Street 工程师 Matthew Saffer 在博客中写道，过去几年大语言模型已经改变了公司写代码、读代码、调试和评审的方式，多数工程师每天都在使用，但传统编程面试却几乎没变：仍是与面试官一起当场做题、边写边谈。今年夏天，他们开始在校园招聘的现场面试中试行新轮次：少写一些代码，更多考察软件设计，以及如何核验代码的质量、结构和意图，也包括使用大模型来产出代码。官方强调，多数轮次仍将是不借助大模型的传统编程面试；并非每次现场都包含新轮次，到场前会提前说明。文章有意写得含糊，称形式仍在演化，不想把六个月后可能已不同的流程写得太死。公司表示，并不要求候选人已经有一套成熟的智能体工作法，关心的是能否想清楚工具的长处、短处以及何时该换工具；资深候选人的面试本就更为多样。

讨论对「改动很小、信息很少」颇有微词，有人直接称之为招聘软文，并追问为何本周连续多篇与 Jane Street 相关的帖子登上首页——解释从营销、高薪与极客声望，到简单的统计波动和「自己刷到一次就会一直刷到」都有。对面试本身，有人认为这不过是业界已流行多年的系统设计加代码理解，只是补上了大模型；也有面试官分享自己的做法：初级必须手写，资深若用模型则要能像自己写的一样解释每一处，或直接改成代码评审。质疑声也不少：几乎没人拿出科学证据证明新流程更能招到合适的人，标题里的对象其实是校园候选人而非所有软件工程师。还有人感慨，白板写代码的时代或许正在过去，将来可能变成「自带提示词和工具链」来面试。

Rust 1.100：never 类型终于稳定

Rust 发布团队于 11 月 12 日宣布 1.100.0。最受关注的是：经过约十年、五次失败的稳定化尝试，never 类型（写作 !）终于稳定。它表示永不会得到值的发散计算，并允许从 ! 强制转换到任意类型；此前虽能在函数返回类型里写 -> !，现在可以在任意位置命名它，例如 Result<T, !>。本次还将 Infallible 改为 ! 的别名，使旧 API 与新写法兼容。为了完成这次改动，2015、2018、2021 版次中的 never 回退类型从 () 改成了 !（2024 版次此前已做），多数代码无感，但在忽略泛型返回值等少见情形下可能表现为破坏性变化，也可能让编译器识别出更多不可达代码。同版本还稳定了分配器 API 的核心部分，允许为 Vec 和 Box 指定自定义分配器；新增 DropGuard，可在变量离开作用域时无条件运行闭包。Cargo 则开始默认警告未使用依赖，并引入最小发布年龄（依赖冷却期）等配置，cargo install 默认改用 crate 包内已有的锁文件。

讨论把这次称为「很久以来最大的发行版之一」。Steve Klabnik 等维护者和贡献者互相致谢，「never finally happened」「这个类型再也不用拿稳定日期开玩笑了」成为高频梗。有人点名喜欢自定义分配器、依赖冷却期，以及 cargo install 默认尊重锁文件这些「跟了很久的补丁」。也有人追问稳定 ABI 和编译速度：维护者解释，泛型使完整的原生稳定 ABI 很难，目前真正稳定的仍是 C ABI；编译时间与目标目录膨胀仍在持续改进，本版本的未使用依赖检查也有助于减少生态里的无效工作。Result::into_ok / into_err 因错过截稿，要等到 1.101。还有人笑称：今天除了黄仁勋的新闻，居然还有别的事发生——只不过 Outlook 挂了，连表情包都不好传。

数学为何无法单独解决软件正确性难题（2016）

Pron 在这篇 2016 年的长文中反驳「只要工具对头，软件正确性就很容易」的说法。文章从希尔伯特计划写起：他曾希望形式系统既一致又完备，并存在判定任意命题是否为定理的算法；哥德尔不完备定理与丘奇、图灵的停机问题，分别击碎了这些支柱。作者进而讨论莱斯定理等结果，认为正确性的代价就像降低熵所要付出的能量，来自计算的「自然定律」，无法被某种语言或证明助手一次性取消。文章并不否定形式方法的价值，但强调其成本很高，且规范本身是否「正确」并不能靠定义自动成立。旧文此刻再度登上首页，显然与当下「用模型大量生成代码、再指望证明或测试兜底」的气氛有关。

讨论并不把这篇十年前的文章当成过时科普。有人高兴能看到在「人工智能会做 Lean」之外，重新讨论形式验证的前提：先把程序设计成可验证的，本身就需要对问题有深入理解。也有人区分数学意义上的正确与真实世界里不断变动的需求，认为关键是判断何时值得证明、何时依靠经验就已足够。对莱斯定理的引用有专业批评，指出它排除的是「对任意程序做统一判定」，并不妨碍为特定、结构良好的程序写出证明。另一些评论把话题拉回 2026：在「能在我机器上跑就算数」被正常化的氛围里，计算可靠性可能被一点点耗掉。也有人觉得标题夸大了，日常工程里人们写代码时已经带着一份大致的正确性论证，悲观的不可判定性并不直接适用于大多数业务程序。

服务稳定性与安全

Humble Bundle 改版后账户安全大幅回退

游戏慈善包平台 Humble Bundle 上线全新网站后，用户在 SpaceBattles、Reddit 等处反映账户安全控制几乎被拆空。多家媒体随后复核：设置页里不再提供双因素认证的添加或更新入口；登录时未必再校验原先的动态验证码，有人改密码时不必输入旧密码，改邮箱时验证也只送到新地址。Kotaku 称自己实测情况属实，并建议先解绑支付信息。《The Verge》写到，自己登录时仍收到邮箱一次性验证码，但改密同样不用旧密码，密码管理器里保存的双重验证也未被要求。除安全问题外，用户还抱怨内容库排序混乱、已兑换与未兑换条目难以区分、无法保持登录，以及误触即完成付款。公司主页目前只确认「焕新外观」，并未就安全回退或是否由人工智能辅助改版作出说明。SpaceBattles 原帖标题把问题归咎于「vibecoding」，但这一归因并无官方证实，更多来自界面风格和通知邮件中出现外部「人工智能安全」公司链接等旁证。

HN 上的争论很快分成两派。一派认为有人在不理解、不验收的情况下把重写直接推上线，不能只把问题归咎于「人工智能写了坏代码」，任何稍有注意的人都能发现双因素和改密校验缺失；另一派则指出，「vibecoding」的要害正在于交付自己没看懂的系统，出事后再把责任推回「还是人的问题」没有意义。有人强调并无直接证据证明站点由模型生成，在人工智能出现之前同样会有不安全的重写，标题有些「凭感觉指控」。实际体验方面，多名用户确认可以绕过双重验证登录，改密不必旧密码，登录过程还会连续遇到多次验证码；也有人误触购买按钮后，PayPal 在无二次确认的情况下扣了款。不少长期订阅者表示将取消订阅，并建议立刻解除自动扣款。讨论把这次改版当成「为大改而大改、上线即比旧版更差」的典型案例。

微软 365 出现大面积服务降级

11 月 12 日，微软 365 出现跨地区服务降级。官方状态页列出受影响的服务包括 Exchange Online、Teams、SharePoint Online、Copilot 365、Defender、Planner、To Do、Intune 以及多项 Purview 与管理中心功能，并称用户可能无法连接多个 365 服务；同期 Azure 状态页则显示暂无活跃事件。CNBC 等报道称，故障约在美东下午 1 点前开始，Downdetector 上 Outlook 相关报告一度约 13 万条。微软对媒体表示，主要问题在 Exchange Online，并感谢用户耐心等待恢复。公司后来解释：最初观察到的「多区域负载升高」，实际是大量服务器意外不可用、健康检查失败，压力被转移到仍在线的机器上。下午 4 点左右，微软称已验证另一种服务健康检查方法，使部分受影响服务器重新上线，并准备用自动化恢复去检测和重启无响应的机器。状态更新还提到，已暂停部署与配置变更，并在部分地点实施保护性流量管理。亚马逊则在社交网络上澄清，自身服务运行正常，外界把问题算到 AWS 头上并不准确。

HN 上的帖子几乎是实时故障墙：有人转贴微软 365 状态账号的声明（事件编号 EX1550543），有人抱怨状态页本身也极慢甚至返回 502，让人联想到「火灾时消防队自己也着火」的笑话。多位系统管理员确认整个组织的 Outlook 不可用，有人以为 AWS、Gmail、Cloudflare「全挂了」，随即被纠正：Downdetector 在大型故障时会把用户误报和社交媒体提到的名字一起算进去，并不能当监测系统用。讨论里还出现对云「没有单点故障」承诺的嘲讽，以及有人把故障与微软近期鼓励部分员工自愿离职的消息联系起来。也有评论指出，使用微软单点登录、Intune 或 Defender 的公司，会感觉「好多不相关的软件都坏了」，其实只是身份和终端链路被拖下水。Azure 在此次事件中相对平稳，成为少数让运维稍微安心的消息。

Apache HTTP Server 曝出严重远程代码执行漏洞

安全公司 Wiz 撰文介绍 CVE-2026-119618：Apache HTTP Server 的 HTTP/2 模块（mod_http2）在 assign_headers() 中存在并发竞态，不当同步共享资源可能导致堆损坏，进而被远程、未认证的攻击者用来执行任意代码。漏洞由 Anthropic 与谷歌云漏洞研究团队独立发现，影响 2.4.55 至 2.4.70，修复版本为 2.4.71 及更新版本；独立维护的 GitHub 版 mod_h2 则需升到高于 2.0.42 的版本。Wiz 称发文时尚无公开利用、也没有野外攻击报告，但根据其数据，64% 的云环境存在易受影响的资源，51% 的云环境有对外暴露的实例（未计入具体配置差异）。若无法立刻升级，权宜之计是关掉 HTTP/2，只保留 HTTP/1.1。值得注意的是，Wiz 文中出现了标题写错 CVE、把托管在 GitHub 上的模块写成「厂商是 GitHub」等硬伤，讨论区有人认为这篇文章本身像是根据补丁和公告生成后再疏于校对的产物。

HN 对「堆损坏是否等于远程代码执行」争得比较激烈：有人主张没有可演示的利用路径就不应把标题写成 RCE；也有人引用红帽说明，称已有针对默认启用 mod_http2 服务器的可靠利用研究，红帽给出的严重性为 9.8。有评论核对修复提交，发现漏洞最早随 2023 年 1 月 17 日的版本引入，远在大模型编程流行之前，一句话补丁也出自 Apache 开发者，并不能当成「Claude 把 Apache 写坏了」的证据。运维讨论则很实际：关掉 HTTP/2、升级到 2.4.71，以及「我的版本太旧反而没中招」的黑色幽默。也有人感叹 Apache 仍服务可观比例的站点，WordPress 官方镜像默认就用它，这次并不是「只有老系统才需要关心」的事件。

海王星外发现可能的新矮行星候选体

《史密森尼杂志》报道，史密森天体物理台的 Matthew Holman 在智利维拉·鲁宾天文台的数据中，注意到一颗显得格外亮、可能很大的天体。他与 Kevin Napier、Mario Jurić 一起在过去十年的巡天照片中找回这颗天体，甚至在哈佛底片库 1937 年的感光板上也能对应到预测位置，从而确认它是真实的。该天体被命名为 2026 ED138，目前距太阳约 46 个天文单位，轨道周期约 281.1 年，轨道面相对太阳系主要行星倾斜近 25 度，暗示曾与海王星发生过引力扰动。它是否能列入矮行星，关键在于尺寸是否足以靠自身引力变成近似球形。目前直径估计大约在 370 英里到 930 英里之间，仅凭亮度无法区分「又小又亮」和「又大又暗」。研究人员计划用红外测热，或观测它遮挡恒星的时间，来约束大小；Holman 表示未来数月观测条件会更好，ALMA 等望远镜可能参与。若确认，它将加入冥王星、阋神星、鸟神星、妊神星和谷神星这一仍很短的名单。

HN 的情绪以惊喜为主，许多人觉得「在 1937 年的底片里就有它」特别动人。反复出现的问题是：这是不是传说中的「X 行星」或「第九行星」？评论普遍给出否定答案——矮行星质量远不足以造成那类轨道扰动。讨论随即滑向 2006 年冥王星「降级」是否正确：有人认为谷神星以及后续发现的同类天体说明分类改得对，也有人强调分类本就带任意性，木星与太阳的质心甚至不在太阳表面之内。有人分享了可交互的轨道可视化，并提醒目录下载较大、更适合桌面浏览。也有细心读者抓到文中早期版本的一处拼写错误（tiled / tilted），争论这是人工智能代笔的痕迹还是杂志编校人手不足。另有评论借题发挥：连太阳系里都还能找到新世界，谈费米悖论或许仍嫌太早。

任天堂在 GitHub 大规模发出 DMCA 下架通知

IGN 报道，任天堂向 GitHub 发出四份 DMCA 通知，目标包括 Switch 模拟器 Yuzu、Citron Neo，以及改机芯片固件。其中改机固件相关仓库约 144 个已被 GitHub 移除并换成下架声明。这类固件可用于为焊在主机主板上的 Picofly 等芯片刷写程序，以绕过任天堂的复制保护。任天堂在 11 月 6 日的通知中称，Switch 主机与游戏包含技术保护措施，只允许主机与正版游戏文件交互，从而阻止盗版及在未授权设备上运行。这并不是任天堂第一次向 GitHub 发函，也不是第一次针对 Yuzu；TorrentFreak 指出，部分固件似乎仍在站点其他位置托管。报道还提到，此次行动出现在《塞尔达传说：时之笛》重制版刚能在电脑模拟器上运行数日之后。文章同时回顾了近期围绕人工智能改版、反编译与再实现的争议，包括游戏厂商对浏览器版或生成式「移植」的打击。

讨论在「游戏保存」与「新作盗版」之间拉锯。有人认为，为自有卡带做备份、在模拟器上运行，本应属于合理使用，但 DMCA 第 1201 条对「提供绕过工具」管得更严，GitHub 作为平台往往会先下再问。也有人指出，多数 Switch 2 模拟器和不少 Switch 1 项目并不在 GitHub，而是自建站点，过几天就会换地方回来，任天堂要的也许只是把当前世代的模拟使用压在边缘。另一些人反感社区把刚上线的新作和十年前的冷门游戏混为一谈，觉得这会连累真正的保存工作。替代托管方案被反复提起，但也有人提醒：域名和服务器提供商同样可能很快关掉，模拟器圈其实早已习惯备份与搬迁。不少用户提到任天堂过往的版权执法，并称将抵制其新主机；也有评论认为，个别抵制很难改变销售基本盘。

数据中心用电成本如何分摊

康奈尔大学新闻稿介绍了发表于《自然·能源》的一项研究。冯琪（Fengqi You）与程峰（Cheng Feng）等人分析 2020 至 2025 年美国四大电网的用电增长与基建项目，发现数据中心推高了批发电价，但在与其增长相关的基础设施费用中，平均只承担了 38%：2025 年 82.5 亿美元账单里，数据中心支付 31.2 亿，其余 51.3 亿（62%）主要由居民承担；最低收入家庭因此增加的能源开支最高可相当于收入的 28%。输电等相关投资从 2020 年的 20 亿美元升至 2025 年的 340 亿美元，数据中心是重要推手。研究预计，到 2030 年数据中心可能占美国用电的 8% 至 17%，其中 70% 至 80% 与人工智能有关。作者同时承认收益：每吉瓦数据中心容量可在经济中创造约 15,000 个就业，与数据中心直接相关的约 2,700 个。受影响最明显的枢纽批发电价到 2025 年上升近 10% 或更多，弗吉尼亚约 15%，加州南湾约 20%；纽约和新英格兰因建设有限，尚未出现同样清晰的涨价。一个关键机制是：电网扩建费用常按既有用电模式分摊，数据中心尚未运行时没有历史负荷，家庭便先扛下大部分成本。农村家庭能源负担偏高（开支超过收入 6%）的增幅，比城市居民高出 76%。

HN 的分歧很清楚。一边问：居民到底得到了什么？数据中心与人争夺电力和基础设施，却常拿到税收优惠，升级电网的钱大部分摊到公众头上；有人举出自己所在地区电费上涨、工人加班却没有相应加薪的例子。另一边则强调就业、税基和把数据中心当成「这一代的核电站」——将来或许会后悔建得太少。也有评论把原因归到供电不足：许多市场十几年没新增足够的基荷电源，许可过严才是电价上涨的根因，只盯着数据中心会找错对象。对论文方法亦有专业质疑，认为按峰值需求增量去「分配」输电升级成本，并不符合电网实际是如何规划和计价的。整体上，读者并不否认有人在为人工智能用电买单，争议在于这个「谁」该是电力用户、纳税人，还是数据中心自己，以及现行分摊规则能不能赶上需求变化的速度。
